なぜ必要か

いちばん危ないのは、
「問題なし」という嘘のレポート

AIによる脆弱性検出には弱点があります。認証エラーやネットワーク断でスキャンが全滅しても、結果は「検出0件」になる。件数だけを見るCIは、これを緑で通します。

つまり 設定ミスが「安全のお墨付き」に化ける。これは脆弱性そのものより危険です。GRIMOIRE は検出結果とは独立に「走査が完走したか」を判定し、完走していなければ検出0件でも終了コード3で止めます。

— --fail-on never でもこの判定は効きます。「検出でCIを落とさない」設定であって、「壊れた走査を成功扱いにする」設定ではないからです。

$ grimoire . --fail-on high ✖ 走査が完走しませんでした（failed） 分析タスクの 10/10 件が失敗しました （APIキー未設定）。検出0件を「安全」と 解釈しないでください。 $ echo $? 3 # 検出0件でも緑にしない
仕組み

7つの工程が、共有モデルを育てていく

前の工程の結果を次が使います。途中が失敗しても、可能な限り部分結果を返します。

④連鎖演算 と ⑤構造把握 は同時に実行。⑥は⑤の結果が無ければ生成しません（推測の土台が無いのに想定リスクは語れないため）。

3つの違い

ただ検出するだけの
スキャナーではありません

Kill Chain

個別の欠陥を「攻撃経路」として繋ぐ

「SSRFがある」「認証が甘い」と羅列するのではなく、どこから侵入し、何を踏み台に、最終的に何を奪われるかを一本の筋書きにします。複数の経路が共通して通る急所（チョークポイント）を先に示すので、1箇所の修正で複数の攻撃を同時に断てます。

Provenance

事実と推測を、混ぜない

「Dockerfileにこう書いてある」は事実。「このサービスは公開されている」は推測。GRIMOIRE は全ての主張に出所を付けて回し、推測には確信度と根拠を添えます。「なんとなくそう見える」を事実として報告しません。

Health Gate

検出0件を「安全」と偽らない

走査が完走したかを検出結果とは別の軸で判定します。認証・通信・予算切れで全滅したら、検出0件でも終了コード3。レポート本文も「検出されませんでした」ではなく「判定できません」に切り替わります。自分で掲げたことを、ツール自身が破らないための仕組みです。

配色にも意味がある

ヒートマップは、2つの層を重ねる

アーキテクチャ構成図の上に、実測（事実）と想定（推測）を独立して重ね、両者の食い違い＝死角を洗い出します。

● Observed — 事実

実測リスク（塗り）

実際に検出された脆弱性です。CVSSと件数から算出し、根拠になったコードを引用できます。

observed: 95  ·  findingIds: [VS-3f9a…]
◌ Inferred — 推測

想定リスク（破線）

CWEカタログとスタック構成から導いた「起こりうる」リスクです。確信度が付きます。

inferred: 72  ·  confidence: 0.6

実測 低 × 想定 高 = 死角。「本当に安全」なのか「まだ見ていないだけ」なのかを切り分けて示します。

カバレッジ

デプロイメントスタックの
どこを見て、どこを見ないか

上ほどコードに近く、下ほどインフラに近い層です。 見ない層を明示するのもカバレッジの一部です — 「検出0件」の意味は、どこを見ていないかを知って初めて決まります。

●
アプリケーションコード
自分で書いたロジック
実測
5つのレンズでLLMが直接読みます（インジェクション / 認可 / 暗号・秘密情報 / デシリアライズ・SSRF / Web出力）。source から sink までのデータフローを根拠として要求し、 自己検証パスで反証を試みます。ここが本体です。
●
依存パッケージ
npm / PyPI / Go / Maven / …
実測
マニフェストから7エコシステムの依存を抽出し、OSV.dev で既知CVEを照合します。 コード解析とは別経路なので、LLMが使えなくてもここは出ます。
◐
フレームワーク / ミドルウェア
Express・ORM・テンプレート等
部分的
使用フレームワークを検出し、その既定の防御を判定に織り込みます （ORMのバインド、テンプレートの自動エスケープなど。効いていれば誤検知として落とす）。 ただしミドルウェア自体の設定や稼働中の状態は見ません。
◌
コンテナ / デプロイ設定
Dockerfile・k8s・Terraform・CI
推測の材料
18種のマニフェストを読みますが、ここから直接Findingは出しません。 露出度・信頼境界・技術スタックを推定する材料として使い、 ヒートマップの想定層（破線）になります。IaCの設定監査そのものは範囲外です。
▲
OS / ホスト
ベースイメージ・カーネル・権限
対象外
ベースイメージのOSパッケージCVE、カーネル、ファイル権限は見ません。 読むのは言語のパッケージマニフェストだけなので、apt/apk 由来の脆弱性は検出されません。 Trivy / Grype などのイメージスキャナと併用してください。
▲
ネットワーク / 物理
L4以下・FW・SG・データリンク
対象外
実行時の通信、ファイアウォール、セキュリティグループ、L2以下は一切見ません。 宣言から「公開されていそうか」を推測するだけです。 ここは動的スキャンやクラウド設定監査の領分です。
● 実測 — 根拠を引用できる ◐ 部分的 — 判定には使うが監査はしない ◌ 推測の材料 — 想定層になる ▲ 対象外 — 死角として明示する

なぜ OSI 7層で描かないのか

OSI参照モデルはプロトコルのカプセル化で切る軸です。この軸で描くと、 GRIMOIRE が見つけるものはほぼ全部が第7層に落ちます。 7層のうち1層だけが点灯し、残る6層が暗い図にしかならず、カバレッジの説明になりません。

さらに悪いことに、この軸では 「自分で書いたコードの欠陥」「依存パッケージの既知CVE」「デプロイ設定からの推測」の違いが消えます。 いずれもL7だからです。実際にはこの3つは別々の仕組みで検出していて、 信頼できる度合いも違います。使う側に効くのは、その差です。

上の軸は「直すには何を変えるか / 誰の持ち場か」で切っています。 アプリの層はコードを直す、依存の層はバージョンを上げる、OS層は別のツールを足す — カバレッジの図が、次の行動にそのまま対応します。

主な機能

実務に必要なものを、ひととおり

◆ CVSS v3.0 / v3.1

基本評価基準を仕様どおり実装。1944通り＋公式サンプルで検証済み。

◆ CWEカタログ 959件

MITRE公式データを圧縮して同梱。実行時にネットワークへ出ません。

◆ 自己検証パス

候補ごとに別プロンプトで反証します。誤検知への主対策です。

◆ SARIF / CIゲート

GitHub Code Scanning連携。差分（新規のみ）でのゲートも可能。

◆ ベースライン差分

前回との new / persistent / fixed を追跡します。負債を増やさない運用にできます。

◆ OSV依存脆弱性照合

依存パッケージの既知CVEをOSV.devで照合。失敗しても走査は継続。

◆ 5つの分析レンズ

インジェクション / 認可 / 暗号・秘密情報 / デシリアライズ・SSRF / Web出力。

◆ 5形式で出力

CLI / JSON / SARIF / Markdown / HTML から用途で選べます。

◆ チャンク単位キャッシュ

変更のないコードは再分析しません。2回目以降は大幅に速く、安くなります。
