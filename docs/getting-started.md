## 1. これは何をするツールか

**あなたのソースコードを読んで、セキュリティ上の欠陥を探し、直す順番を提案します。**

普通の静的解析ツール（ESLint など）との違いは3つです。

**① AIがコードの意味を読む。**
「この関数の引数はHTTPリクエストから来ていて、それが検証されずにSQL文に埋め込まれている」
というような、**離れた場所どうしの繋がり**を追えます。
パターンマッチではないので、見慣れない書き方でも気づけます。

**② 個別の欠陥ではなく「攻撃の筋書き」を出す。**
「SSRFがある」「認証が甘い」と個別に並べるのではなく、
「ここから侵入 → これを踏み台に → 最終的にこうなる」という経路として組み立てます。
単体では中リスクでも、繋がると致命的になるものを見つけるためです。

**③ 直す順番を決めてくれる。**
100件並べられても困ります。複数の攻撃経路が共通して通る「急所」を先に出すので、
**1箇所直すだけで複数の経路を断てる**ところから着手できます。

### 向いていること・向いていないこと

| | 内容 |
|---|---|
| **向いている** | Web API・サーバサイドアプリのロジックに潜む欠陥。既知CVEを含む依存パッケージ |
| **向いていない** | 実行時にしか分からない問題（設定ミス・権限設定）。網羅的な保証 |

**このツールは「脆弱性が無いこと」を証明できません。**
見つかったものを報告するだけです。見つからなかったことは何の保証にもなりません。
大事な点なので §6 でもう一度扱います。

## 2. 仕組みをざっくり

7つの工程を順に通します。前の工程の結果を次が使う、という流れです。

```
  ① 索敵      リポジトリを読んで地図を作る
                ファイル一覧・関数の位置・呼び出し関係・
                「外部からの入口」と「危険な処理」の場所
                    ↓
  ② 解析詠唱   AIがコードを読んで脆弱性を探す ★中核
                関数単位に切り、5つの観点それぞれで走査。
                見つけた候補は別のAIに反証させる（誤検知対策）
                    ↓
  ③ 照合      検出結果を整える
                CVSSスコア算出・重複統合・CWE分類・
                依存パッケージの既知脆弱性(OSV)照合・前回との差分
                    ↓
      ┌─────────────┴─────────────┐   ← この2つは同時に走ります
  ④ 連鎖演算                  ⑤ 構造把握
    個別の検出を                 システム構成と
    攻撃経路として繋ぐ            デプロイ先を推定する
      └─────────────┬─────────────┘
                    ↓
  ⑥ 熱図描画   「どこが危ないか」を構成図の上に重ねる
                    ↓
  ⑦ 編纂      優先順位を決め、読める文章にする
```

### なぜAIを使うのか、どこまで信じるのか

AIに任せているのは**判断が要る部分だけ**です。

| AIがやること | 機械（決定的な計算）がやること |
|---|---|
| 脆弱性かどうかの判定 | CVSSスコアの計算 |
| 攻撃経路の推論 | 優先順位のスコアリング |
| 文章の執筆 | 集計・重複統合・差分 |
| 構成の推測 | ヒートマップの算出 |

**数字と順序は必ず機械が出します。** AIが使えなくても集計と優先順位は出ますし、
同じ入力からは必ず同じ順序のレポートが出ます。

### 「事実」と「推測」を混ぜません

このツールの重要な性質です。たとえば:

- 「Dockerfile に `FROM node:20` と書いてある」→ **事実**（引用できる）
- 「このサービスはインターネットに公開されている」→ **推測**（確信度が付く）

レポートでは両者を区別して表示し、推測には確信度と根拠が付きます。
**「なんとなくそう見える」を事実として報告しない**ための仕組みです。

### 誤検知への3段構えの対策

AIによる脆弱性検出の最大の弱点は「それっぽい嘘」です。対策は3つ。

1. **根拠を必須にする** — 「どの入力がどこを通ってどこに届くか」を出せない指摘は受け付けない
2. **反証させる** — 別のAIに「これは成立しないはずだ」と反論させ、
   論破されたものは捨て、判断がつかないものは確信度を下げる
3. **足切り** — 確信度が一定未満は表示しない（既定 0.5）

## 3. 準備する

### 必要なもの

- **Node.js 20 以降** — `node -v` で確認
- **Anthropic の APIキー** — [console.anthropic.com](https://console.anthropic.com/) で取得
- **お金** — AIの利用料がかかります（§9 参照）

### セットアップ

```bash
cd vulnscan
npm install
npm run build
```

`npm run build` は TypeScript のコンパイルに加えて、
CWEカタログ959件を `dist` へコピーします（このコピーが無いとカタログが空になります）。

### APIキーを設定する

```bash
export ANTHROPIC_API_KEY="sk-ant-..."
```

毎回打つのが面倒なら `~/.zshrc` や `~/.bashrc` に書いておきます。

> **キーをリポジトリにコミットしないでください。**
> `.env` に書く場合は `.gitignore` に入っているか必ず確認してください。
> 皮肉な話ですが、このツールが最初に見つける脆弱性が自分のAPIキーだった、
> というのは実際によくあります。

### コマンドを使えるようにする

3つのやり方があります。好きなものを選んでください。

```bash
# A) ビルド済みを直接叩く（一番確実）
node dist/cli/index.js /path/to/repo

# B) グローバルに登録する（どこからでも grimoire で呼べる）
npm link
grimoire /path/to/repo

# C) ビルドせずソースから走らせる（開発時）
npm run dev -- /path/to/repo
```

以降このガイドでは `grimoire` と書きます。B以外の人は読み替えてください。

## 4. はじめてのスキャン

### まず小さく試す

いきなり大きなリポジトリに向けると、時間もお金もかかります。
**最初は観点を1つに絞り、思考の深さを落として**、動くことの確認から始めてください。

```bash
grimoire ./my-app --lens injection -e low --no-kill-chain --no-architecture
```

| 指定 | 意味 |
|---|---|
| `--lens injection` | インジェクション系の観点だけ見る（5観点→1観点） |
| `-e low` | AIの思考を浅く・速く・安く |
| `--no-kill-chain` | 攻撃経路の推論を省く |
| `--no-architecture` | 構成推定とヒートマップを省く |

走っている間、こういう表示が出ます（対応する工程が終わるたびに1行確定します）。

```
✦ GRIMOIRE — 禁書「九五九」を開きます
✔ [1/7] 索敵（コンテキスト収集） — 128 ファイル 0:02
◓ [2/7] 解析詠唱 走査 ▓▓▓▓▓░░░░░░░ 34/85 タスク 0:41
```

**`[1/7] 索敵` の件数を必ず見てください。** ここが想定と違えば、それ以降は
見当違いの範囲を分析していることになります。違ったら `Ctrl+C` で止めて、
`include` / `exclude` の設定を直してください。

終わると、どれだけ見ていくら使ったかが出ます。

```
処理: 128 ファイル / 18,452 行 / 17秒
トークン使用量: 入力 412,338 / 出力 38,112 (キャッシュ読み 286,004 / 書き 9,820)
```

**この2行で費用の見当がつきます。** 小さい範囲で1回計ってから、
ファイル数の比で本番を見積もるのが確実です。

キャッシュ読みの数字が大きければ、前回の結果が再利用されています
（チャンク単位でディスクにキャッシュされ、保存先は走査対象側の `.grimoire/cache/`）。
同じ対象・同じ設定なら2回目はほとんど課金されません。

うまくいったら、全部入りで走らせます。

```bash
grimoire ./my-app
```

### 結果をファイルに残す

CLI表示は要約です。**全件を見るならHTMLかMarkdownを出してください。**

```bash
grimoire ./my-app -f html -o report.html     # ブラウザで開く。構成図つき
grimoire ./my-app -f markdown -o report.md   # PRに貼る
grimoire ./my-app -f json > report.json      # スクリプトで処理する
grimoire ./my-app -f sarif -o report.sarif   # GitHub Code Scanning に食わせる
```

HTMLだけ、**システム構成図の上にリスクを重ねた図**が付きます。
どこが危ないかを一目で見たいときはこれが一番早いです。

> **出力先の約束**: レポート本体は必ず stdout、進捗やエラーは stderr に出ます。
> `grimoire -f json > out.json` は常に正しいJSONになります。

## 5. レポートの読み方

実際の出力です。上から順に説明します。

```
━━━━━━━━━━━━━━━━━ GRIMOIRE スキャン結果 ━━━━━━━━━━━━━━━━━
対象: /home/user/app  ブランチ: main@abcdef12
ファイル 128 / 所要 17.4秒 / 依存 34 / 入口 7

▍走査対象
  対象        /home/user/app
  実施日時    2026-08-05 14:22:07（所要 17秒）
  Git         main @ abcdef12
  規模        128 ファイル / 18,452 行 / 1.2 MB / typescript 88% json 6%
  検出FW      Express, PostgreSQL

  これは何か
    my-app — 社内向けの在庫管理API。Express + PostgreSQL。
    （README.md からの引用）
    様式の推測: SPA + API 確信度 0.70

  構成（上位2階層）
    src/                               112 ファイル
      api/                              38
      auth/                             12
      db/                                9
    test/                               14 ファイル
    (ルート直下)                         2 ファイル
```

**まずここを見てください。** 検出内容より先に、「何をどこまで見た結果なのか」が分かります。
数週間後に読み返すのは自分で、そのときにはどのディレクトリにどの設定で当てたかを覚えていません。

- `規模` … 実際に走査したファイル数・行数。**意図した範囲になっているか必ず確認してください。**
  `include` / `exclude` の設定ミスは、ここの数字が想定と違うことで気づけます
- `これは何か` … README の見出しと導入段落の**引用**です。要約も言い換えもしません。
  引用元のファイル名が併記されるので、原文に当たれます
- `様式の推測` … 確信度つき。こちらは**推測**なので、引用とは行を分けています
- `構成` … 10ファイル以下ならファイル名をそのまま列挙、超えたら上位2階層の集計。
  表示を打ち切った場合は「表示を省略したディレクトリ: …」と件数が出ます

README が無い対象では「取得できていません」と明示します。黙って省略はしません。

```
▍深刻度別の検出状況
  緊急 critical    1  ████████████████████████████████████
  高 high         1  ████████████████████████████████████
  中 medium       1  ████████████████████████████████████
  合計 3 件  |  攻撃チェーン 1 本  |  最大CVSS 9.8
  新規 2  |  継続 1  |  解消 0
```

**深刻度は5段階**（緊急 / 高 / 中 / 低 / 情報）。棒グラフは最大件数を基準にした相対表示です。

`新規 / 継続 / 解消` は前回スキャンとの差分です（§7 のベースラインを設定すると出ます）。
**継続的に使ううえで一番大事な数字**で、「増えているか減っているか」が分かります。

```
▍エグゼクティブサマリ
  128 ファイルの走査で 3 件のセキュリティ上の問題を検出しました（うち至急対応
  すべき「緊急・高」が 2 件）。特に注意が必要なのは、GET /api/users/:id を
  起点として全ユーザーの個人情報の閲覧と管理者権限の奪取 に至る攻撃経路が
  1 本成立しうる点です（成立可能性: 高）。まず着手すべきは…
```

**非技術者に見せる部分。** 「何が起きうるか」「事業上どう困るか」「まず何をすべきか」の3点だけ。
上長への報告はここをコピーすれば足ります。

```
▍上位の攻撃チェーン（全 1 本）
  [ 92] SQLインジェクション経由で認証情報を奪取し横展開
        起点 GET /api/users/:id / 成立可能性 高 / 2 ステップ
        影響: 全ユーザーの個人情報の閲覧と管理者権限の奪取
        ✂ チョークポイント: VS-3f9a1c04b2d7
```

**このツールの中核。** 個別の欠陥ではなく攻撃の筋書きです。

- `[ 92]` … 優先度スコア（0-100）。連鎖の成立しやすさと影響から算出
- `起点` … 攻撃者が最初に触れる場所
- `成立可能性` … 高 / 中 / 低
- **`✂ チョークポイント`** … **ここを直せば連鎖全体が断てる**という急所。
  複数のチェーンが同じ箇所を通っていれば、1回の修正で複数の経路を潰せます

```
▍優先対応アクション
  1. [工数:小] プレースホルダを用いたパラメータ化クエリに書き換える
               （CWE-89 / src/api/users.ts）
     └ 解消: Finding 1 件 / チェーン 1 本を遮断
  2. [工数:小] 許可リストでホストを制限し、内部アドレスへの解決を拒否する
               （CWE-918 / src/api/proxy.ts）
     └ 解消: Finding 1 件
```

**上から順に着手してください。** 順番は機械が決めています（AIの気分ではありません）。

優先度の考え方は「チョークポイント > 複数の攻撃経路に登場 > CVSS > 深刻度」。
つまり**単独で高スコアな孤立した問題より、中スコアでも複数の経路の要になっている問題を上に出します**。

`解消:` は「この1つの作業で何件片付くか」。同じ直し方で済むものはまとめてあります。
`工数` は 小 / 中 / 大 の見積もりで、依存パッケージなら修正版の有無、
コードならファイル数・CWEの性質・データフローの長さから機械的に推定しています。

```
▍検出一覧（上位 3 件）
   緊急  9.8 SQLクエリへのユーザー入力の直接連結
        CWE-89  src/api/users.ts:42  [VS-3f9a1c04b2d7] new
   高    8.6 外部から渡されたURLをそのまま fetch している
        CWE-918  src/api/proxy.ts:88  [VS-8b21e7d5a0c3] new
   中    5.3 APIトークンがソースに直書きされている
        CWE-798  src/config/keys.ts:12  [VS-c40d92f18ae6] persistent
```

- `9.8` … CVSSスコア（0.0-10.0）。国際標準の深刻度指標
- `CWE-89` … 弱点の分類番号。[cwe.mitre.org](https://cwe.mitre.org/) で調べられます
- `[VS-3f9a1c04b2d7]` … このFindingのID。抑制リストで使います。
  位置とCWEから決定的に導出しているので、コードが動かない限り毎回同じIDになります
- `new` / `persistent` / `fixed` … 前回との差分

CLIには上位10件しか出ません。`--verbose` で全件、あるいはHTML/Markdownを見てください。

### 個別のFindingで必ず見るもの

HTML/Markdownの詳細では、1件ごとに以下が付きます。

| 項目 | 見方 |
|---|---|
| **データフロー** | `source`（入力元）→ `propagation`（経由）→ `sink`（危険な処理）。**ここが空なら「到達経路が証明できていない」** ので、鵜呑みにせず自分で確認 |
| **確信度** | 0.0-1.0。自己検証パスを通した後の値。0.5-0.6 なら疑ってかかる |
| **reasoning** | なぜ脆弱だと判断したか。**ここに納得できなければ誤検知を疑ってよい** |
| **remediation** | 修正方針 |

**確信度が高くても間違っていることはあります。** 最終判断は必ず人がしてください。

## 6. 「検出0件」の正しい読み方

**このツールで一番大事な話です。**

```
✔ 対応を要する脆弱性は検出されませんでした
```

これは「安全」という意味ではありません。**今回の観点と対象範囲では見つからなかった**、それだけです。
除外設定で対象外になっていたファイルや、有効にしていない観点の問題は出ません。

もっと厄介なことがあります。**スキャン自体が失敗していても、検出は0件になります。**
APIキーが間違っていれば全タスクが失敗し、結果として「0件」になるからです。

そこでこのツールは、検出結果とは**別の軸**で「走査が完走したか」を判定します。
完走していないときは、件数を出す前にこう出ます。

```
▍⚠ 走査は完走しませんでした
  分析タスクの 10/10 件が失敗しました（失敗 10 / 拒否 0）。検出結果は信頼できません。
  分析タスク: 成功 0 / 失敗 10 / 拒否 0 / 全 10
  この結果に「脆弱性が無い」ことの根拠としての意味はありません。

▍深刻度別の検出状況
  ✖ 検出0件。ただし走査が完走していないため判定できません
```

**このとき終了コードは `3` になり、CIは赤くなります。** これは意図的な設計です。
壊れたスキャンを緑で通すと、「チェック済み・問題なし」という誤った記録が残るからです。

### 終了コードの意味

| コード | 意味 | やること |
|---|---|---|
| `0` | 完走し、閾値以上の検出なし | 進める |
| `1` | 閾値以上の検出あり | レポートを読んでトリアージ |
| `2` | コマンドや設定の誤り | コマンドを直す |
| `3` | **走査が完走しなかった** | APIキー・ネットワーク・予算を直して再実行 |

`1` と `3` を分けているのは、**対応が全く違うから**です。
`1` はコードを直す話、`3` はツールを動くようにする話です。

## 7. 誤検知とのつきあい方

AIによる検出には誤検知が混ざります。付き合い方は2つ。

### ベースライン — 「今ある分は一旦置いておく」

既存のコードベースに初めて使うと、大量に出てきて手が付けられないことがあります。
そういうときは**現状を基準点として記録**し、以後は新しく増えた分だけを見ます。

```bash
# 現状をベースラインとして記録
grimoire ./my-app --update-baseline

# 以後は新規分だけでCIを落とす
grimoire ./my-app --fail-on high --fail-on-new-only
```

記録先は `.grimoire/baseline.json`。**これはコミットしてください**（チームで共有するため）。

以後のスキャンでは各Findingに `new` / `persistent` / `fixed` が付き、増減が分かります。

> **⚠ 現在の制限: 失敗したスキャンでも `--update-baseline` はベースラインを上書きします。**
>
> APIキー切れなどでスキャンが完走しなかった場合、検出は0件になります。
> その状態で `--update-baseline` を付けていると、
> **記録済みのFindingがすべて「解消された」とみなされ、ベースラインが空になります。**
> トリアージ済みの状態（`confirmed` / `accepted`）や `firstSeen` の履歴も消えます。
>
> 安全側の壊れ方（次回すべてが `new` として再び出るので、見逃しにはなりません）ですが、
> 積み上げた記録は失われます。**回避策**: `--update-baseline` を使う場合は
> 終了コードを確認し、`3` のときはベースラインの変更を捨ててください。
>
> ```bash
> grimoire . --update-baseline || {
>   code=$?
>   [ "$code" -eq 3 ] && git checkout -- .grimoire/baseline.json
>   exit "$code"
> }
> ```
>
> 定期実行のジョブで `--update-baseline` を無条件に付けるのは避けてください。

### 抑制リスト — 「これは誤検知だと確定した」

個別に消したいものは `.grimoireignore` に書きます。1行1エントリ、`#` 以降はコメントです。

```
# Finding ID を指定（レポートの [VS-...] をそのまま貼る）
# 誤検知。この値はユーザー入力ではなく起動時に読む設定ファイル由来
VS-c40d92f18ae6

# CWE 単位で消す（影響が大きいので慎重に）
CWE-798

# ファイルパスの glob で消す
# 移行予定の旧実装。2026Q3に削除するのでそれまで抑制
src/legacy/**

# glob と CWE の AND 条件（この範囲のこのCWEだけ）
src/legacy/** CWE-89
```

書けるのは「Finding ID」「CWE ID」「glob」「glob + CWE」「指紋（16-64桁の16進）」の5種類です。

> **抑制は最後の手段です。** 「よく分からないから消す」は最悪の使い方で、
> 本物の脆弱性を自分の手で隠すことになります。
> **なぜ誤検知なのかをコメントに書いてください。** 半年後の自分と同僚のためです。

### 判断に迷ったら

- **データフローが空** → 到達経路が証明されていない。優先度を下げてよい
- **確信度が 0.5-0.6** → 自己検証でも判断がつかなかった。人が見る価値がある
- **reasoning に納得できない** → 誤検知の可能性が高い。ただし消す前に一度実物を確認

## 8. CIに組み込む

GitHub Actions の例です。

```yaml
name: security-scan
on: [pull_request]

permissions:
  contents: read
  security-events: write     # SARIF のアップロードに必要

jobs:
  grimoire:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: 20

      # GRIMOIRE 自体をビルドする（別リポジトリに置いている場合は
      # そちらを checkout してから同じことをする）
      - name: GRIMOIRE を用意
        working-directory: vulnscan
        run: |
          npm ci
          npm run build

      - name: スキャン
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: |
          node vulnscan/dist/cli/index.js . \
            --fail-on high \
            --fail-on-new-only \
            -f sarif -o results.sarif

      - name: 結果をGitHubに登録
        if: always()             # スキャンが落ちても結果は上げる
        uses: github/codeql-action/upload-sarif@v3
        with:
          sarif_file: results.sarif
```

APIキーは必ず**リポジトリの Secrets** に入れてください（Settings → Secrets and variables → Actions）。
ワークフローに直接書くと、そのリポジトリを読める全員に漏れます。

差分判定（`--fail-on-new-only`）に使うのはコミットした `.grimoire/baseline.json` なので、
`fetch-depth` を広げる必要はありません。

導入時のおすすめ設定:

| 段階 | 設定 | ねらい |
|---|---|---|
| 導入直後 | `--fail-on never` | まず結果を眺める。CIは落とさない |
| 慣れてきたら | `--fail-on critical --fail-on-new-only` | 新規の致命傷だけ止める |
| 定着したら | `--fail-on high` | 高以上を止める |

`--fail-on-new-only` を付けると、既存の負債ではCIが落ちません。
**「今日から増やさない」から始めるのが現実的**です。

> **注意**: `--fail-on never` にしても、**走査が完走しなかった場合（終了コード3）は落ちます**。
> これは「検出結果でCIを落とさない」設定であって「壊れたスキャンを成功扱いにする」設定ではないためです。
> どうしても無効化する場合だけ `--no-fail-on-incomplete` を付けてください。

## 9. 費用と時間を抑えるコツ

このツールはAIを大量に呼びます。**何もしないと高くつきます。**

コストはおおよそ「**対象ファイル数 × 有効な観点の数**」に比例します。
5観点すべてを有効にすると、単純に5倍のAI呼び出しが走ります。

### 効く順に

**① 対象を絞る** — 一番効きます。`.grimoire.yml` で除外設定を書いてください。

```yaml
scan:
  exclude:
    - '**/node_modules/**'
    - '**/dist/**'
    - '**/*.test.ts'      # テストコードは通常見なくてよい
    - '**/migrations/**'
```

**② 思考の深さを落とす** — `-e low` から始めて、必要に応じて上げる。

**③ 観点を絞る** — Web APIなら `--lens injection authz deserialization-ssrf` で十分なことが多い。

**④ 予算に上限をかける** — 事故防止。超えたら打ち切ります。

```bash
grimoire . --budget 200000
```

> 打ち切られた場合は**未走査の範囲が残る**ので、終了コードは `3` になります。
> 「安く済んだ」ではなく「見きれていない」という結果です。

**⑤ キャッシュを効かせる** — 既定で有効です。
変更のないファイルは再分析されないので、2回目以降は大幅に速く・安くなります。
`.grimoire/cache` を消さないでください（`.gitignore` には入れてください）。

**⑥ 工程を落とす** — `--no-kill-chain` / `--no-architecture` / `--no-self-verify`。
ただし `--no-self-verify` は**誤検知が明確に増えます**。速度のために精度を捨てる判断なので、
本番運用では推奨しません。

## 10. 困ったときは

### `Could not resolve authentication method`（終了コード3）

APIキーが設定されていません。

```bash
echo $ANTHROPIC_API_KEY     # 空なら未設定
export ANTHROPIC_API_KEY="sk-ant-..."
```

### 「分析対象のコードがありませんでした」（終了コード3）

除外設定が効きすぎているか、対応していない言語です。
深く解析できるのは TypeScript / JavaScript / Python / Go / Java / Ruby / PHP / Vue / Svelte の9言語です。

`.grimoire.yml` の `scan.exclude` と `scan.include`、それに `.gitignore` を確認してください
（`.gitignore` されたファイルは走査対象外です）。
レポート末尾の「実行時の問題」にも、除外や読み込み失敗の理由が出ています。

### 「安全分類器に拒否されました」

脆弱性の解析はセキュリティ領域の入力を扱うため、AIの安全機構が稀に反応します。
ツール側で自動的に代替モデルへ切り替えるので、**数件なら無視して構いません**。
大量に出る場合は該当ファイルを除外してください。

### `トークン予算を使い切ったため、以降の分析を打ち切りました`

`--budget` の上限に達しました。**残りは走査できていません**（だから終了コード3です）。
上限を上げるか、対象を絞ってください。

### 遅い

- `-c 8` で並列数を上げる（APIのレート制限に当たったら下げる）
- `-e low` で思考を浅く
- `--lens` で観点を絞る
- 2回目以降はキャッシュが効くので速くなります

### 同じ脆弱性が何度も出る

同じ修正で片付くものは「優先対応アクション」でまとめられています。
そちらを見てください。個別リストは網羅のために全件出しています。

### CIが落ちる理由が分からない

終了コードを確認してください（§6の表）。
`1` ならレポートに理由が出ています。`3` なら stderr の最終行に理由が1行出ます。

```
✖ 走査が完走しませんでした（failed）: 分析タスクの 10/10 件が失敗しました…
```

## 11. 用語集

| 用語 | 意味 |
|---|---|
| **CWE** | 弱点の分類番号。`CWE-89` はSQLインジェクション。国際的な共通語彙 |
| **CVE** | 個別の脆弱性に振られる番号。主に依存パッケージの既知問題に付く |
| **CVSS** | 深刻度の国際標準スコア（0.0-10.0）。9.0以上が Critical |
| **OWASP Top 10** | Webアプリで頻出する脆弱性の分類。`A03:2021-Injection` など |
| **source / sink** | `source` は外部からの入力の入口、`sink` は危険な処理の場所。この間が繋がっていると脆弱性 |
| **データフロー** | source から sink までの値の通り道。**これが脆弱性の証拠** |
| **エントリポイント** | 外部から到達できる入口（HTTPルート・CLIコマンドなど） |
| **信頼境界** | 信頼できる側とできない側の境目。跨ぐ場所が危ない |
| **キルチェーン** | 攻撃の段階（偵察 → 侵入 → 実行 → 権限昇格 → 横展開 → 持ち出し） |
| **MITRE ATT&CK** | 実際の攻撃手口を体系化したナレッジベース |
| **チョークポイント** | 複数の攻撃経路が共通して通る急所。**ここを直すと一気に効く** |
| **死角 (blind spot)** | 検出は無いが、構成上リスクが高いはずの箇所。「本当に安全」なのか「見ていないだけ」なのかを切り分けて表示します |
| **ベースライン** | 前回スキャンの記録。差分の基準点 |
| **確信度 (confidence)** | その指摘が正しい見込み（0.0-1.0） |
| **レンズ** | 分析の観点。5種類（インジェクション / 認可 / 暗号・秘密情報 / デシリアライズ・SSRF / Web出力） |
| **チャンク** | AIに渡すコードの単位。関数やクラスなどの構文単位で切ります |
